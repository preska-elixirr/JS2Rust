Null and errors

Rust has no null, no undefined and no exceptions. A value that might be missing is an Option. An operation that might fail returns a Result. Both show up in the type, so the compiler makes you deal with them.

You will learn

  • How Option replaces null, ?. and ??
  • How Result replaces throw and try / catch
  • The ? operator, which lets errors bubble up like exceptions do
  • When a panic is fine, and how to build your own error types with thiserror and anyhow

There is no null: meet Option

In JavaScript any value can be null or undefined, and TypeScript only helps if strict mode is on. In Rust a normal value is never missing. When it can be missing, its type is Option<T>, which is either Some(value) or None.

You cannot reach the User without unpacking the Option first. The two common ways are if let (one case) and match (both cases). Lesson 9 explains both in detail.

Mental model

Option<User> is a box that holds one user or nothing. A User is the user itself. They are different types, so you can never mix them up by accident. The "billion-dollar mistake" of null cannot happen.

Optional chaining and nullish coalescing

?. and ?? are the tools you reach for daily in TypeScript. Rust has methods on Option that do the same jobs.

  • map runs a function on the value if there is one, and keeps None as None. Use it when the function returns a plain value.
  • and_then does the same, but the function itself returns an Option. Use it to chain steps that can each be missing. It is the flatMap of options.
  • unwrap_or(x) gives the value, or x if there is none. That is ??.
  • as_ref() and as_deref() let you look inside an Option field without taking it out of the struct.

The ? operator on Option

Inside a function that returns an Option, you can put ? after any Option. If it is None, the function returns None right away. If it is Some, you get the value and keep going. This reads much like a chain of ?..

Three ways to write ??

RustJavaScriptWhen
opt.unwrap_or(0)x ?? 0The default is a cheap, ready value

Trap

unwrap_or(expensive()) always calls expensive(), even when the value is there, because Rust evaluates arguments before the call. JavaScript's ?? skips the right side. Use unwrap_or_else to get the lazy behavior.

There is no || version with truthy and falsy values. An empty string or a zero inside Some is still a value. If you want to treat it as missing, say so: opt.filter(|s| !s.is_empty()).

The ! assertion becomes unwrap and expect

TypeScript's non-null assertion x! tells the compiler "trust me, it is there". Rust has unwrap() for the same job. The difference is what happens when you are wrong. TypeScript lets the bad value flow on. Rust stops the program right there with a panic.

unwrap is fine in examples, tests, quick scripts, and in spots where a missing value really means a bug in your code. In application logic, prefer match, if let, unwrap_or or ?. When you do use it, expect with a clear message makes the crash easy to trace.

Errors are values: meet Result

In JavaScript, any function can throw, and nothing in its signature tells you so. In Rust, a function that can fail returns Result<T, E>. That is either Ok(value) or Err(error). The caller sees the possible failure in the type and must handle it.

Trap

If you call a function that returns a Result and ignore it, Rust warns: "unused `Result` that must be used". Errors cannot be silently swallowed by accident. To ignore one on purpose, write let _ = save();.

The ? operator: let it bubble up

Most of the time you do not handle an error where it happens. You let it travel up to a caller that knows what to do. JavaScript does this for free: exceptions bubble up until something catches them. Rust does it with one character, ?.

Without ?, every call would need its own match. With it, the happy path reads top to bottom like JavaScript, but every place that can fail is marked with a visible ?.

  • ? only works inside a function that returns Result (or Option, for options).
  • It converts the error into the function's error type on the way out. That is why one function can bubble up both an io::Error and a ParseIntError as Box<dyn Error>.
  • Box<dyn Error> means "any kind of error". It is the easy choice for scripts and small apps.

Tip

To change an error before it goes up, like catching and rethrowing a nicer one, use map_err: text.parse().map_err(|_| "bad port".to_string())?.

panic! vs throw

Rust does have a crash: panic!. It looks like throw, but it plays a different role. A panic means "this is a bug, stop now". You do not catch panics to handle normal failures.

Things that panic for you include unwrap() on None or Err, indexing past the end of a list, dividing an integer by zero, and integer overflow in debug builds.

Your own error types

In JavaScript you subclass Error and check with instanceof. In Rust you make an enum with one variant per kind of failure. Then callers can match on exactly the cases they care about.

Display gives the error its message. The empty impl std::error::Error marks it as a real error type, so it works with Box<dyn Error> and with other libraries.

Less typing: thiserror and anyhow

Writing Display by hand gets old fast. Almost every Rust project uses one or both of these two crates.

thiserror: define error enums in a few lines

You put the message on each variant as an attribute, and the crate writes the Display and Error code. #[from] also lets ? convert another error into your variant automatically.

anyhow: one error type for your whole app

In an application, you mostly want to bubble errors up and print them with useful context. anyhow::Result<T> accepts any error, and .context() adds a line that explains what you were doing, like wrapping an error with a cause in JavaScript.

With anyhow, use .context("text") for a fixed message and .with_context(|| ...) when you build the message with format!.

main can return a Result

If main returns Result, you can use ? in it. When an error reaches the top, Rust prints Error: followed by the error, and the program exits with code 1. It is similar to an uncaught exception in Node, without the stack trace noise.

The Ok(()) at the end means "success, with nothing to return". () is the unit type from lesson 2.

Moving between Option and Result

You often have an Option but your function returns a Result, or the other way around. These methods convert.

The first line is like writing if (!user) throw new Error("user not found") in JavaScript. Use ok_or_else when building the error takes work, for the same reason as unwrap_or_else.

A list of Results becomes a Result of a list

When you parse many items, you usually want "all of them, or the first error". collect() does this when you ask for a Result<Vec<T>, E>. It stops at the first Err.

The same trick works for Option: collecting into Option<Vec<T>> gives None if any item is None. Lesson 7 covers map, filter_map and collect.

Check yourself

What is the Rust version of user?.email ?? "none", where user is an Option<&User>?

user.map(|u| u.email.as_str()).unwrap_or("none").

Where can you use the ? operator?

Inside a function that returns Result (for Result values) or Option (for Option values). That includes main if it returns a Result.

Why is unwrap_or_else(|| load()) often better than unwrap_or(load())?

unwrap_or evaluates load() every time, even when the value exists. The closure in unwrap_or_else runs only when it is needed.

A user typed an invalid email. Do you return an Err or call panic!?

Return an Err. Bad input is an expected problem. Panics are for bugs in your own code.

You are building a CLI tool and want simple errors with context. Which crate do you pick?

anyhow. Use thiserror when you write a library whose callers need to match on specific error kinds.
