Lesson 05 · The new idea

Ownership and borrowing

JavaScript has nothing like this. Every Rust value has one owner, and the owner frees it. Once this idea clicks, the rest of Rust stops feeling strange.

You will learn

  • Why Rust has no garbage collector, and what it does instead
  • What the stack and the heap are, in plain terms
  • Why let b = a; moves a value instead of sharing it
  • How to borrow with & and &mut, and the "many readers or one writer" rule
  • What lifetimes are, and how to read the borrow checker's errors

Why Rust has no garbage collector

Every program has to free memory it no longer needs. Languages pick one of three ways to do it.

StrategyLanguagesWho frees memoryThe cost
ManualC, C++You call free() yourselfForget it and you leak. Do it twice and you crash.
Garbage collectorJavaScript, Java, Go, PythonA background process that scans for unused valuesExtra memory and CPU, plus short pauses you cannot control.
OwnershipRustThe compiler inserts the free at the right spotYou follow a few rules. The compiler checks them.

In JavaScript you create objects and forget about them. Some time later the garbage collector notices that nothing points to an object and frees it. That is easy for you, but the engine does work at runtime to make it happen.

Rust decides at compile time where each value gets freed. There is no collector running next to your program. That is a big reason Rust programs are fast and use little memory.

Mental model

Ownership is the compiler doing the garbage collector's job before the program runs. To do that job, it needs your code to follow clear rules about who owns what.

The stack and the heap

Memory comes in two kinds. JavaScript hides both from you. In Rust you need a rough picture of them, because ownership is about the heap.

  • The stack holds values with a size known at compile time: numbers, booleans, chars. Each function call gets a slot. When the function returns, its slot is gone. This is very fast and needs no cleanup.
  • The heap holds data that can grow or whose size is unknown in advance: the text of a String, the items of a Vec. Something has to free it when it is no longer needed. That something is the owner.

The three ownership rules

That is the whole system. Everything else on this page follows from these three lines.

  1. Each value has one variable that owns it.
  2. A value has exactly one owner at a time.
  3. When the owner goes out of scope, Rust frees the value.

"Out of scope" means the closing curly brace of the block where the variable lives. Rule 3 is how memory gets freed without a garbage collector. Rule 2 makes sure the same memory is never freed twice.

JavaScript shares, Rust moves

Here is the first real surprise. In JavaScript, assigning an object to another variable copies the reference. Both variables point to the same object. In Rust, assigning a heap value moves it. The new variable becomes the owner, and the old one is no longer usable.

Why not let both own it? Because of rule 3. At the end of the scope Rust would free the text once for a and once for b. Freeing memory twice is a classic C bug that can crash a program or open a security hole. Moving makes it impossible.

Trap

A move is silent. let b = a; looks exactly like a JavaScript assignment. You only find out when you use a again and the compiler says "value moved here". Read the error: it shows the line where the move happened.

Small values are copied, not moved

If moving were the rule for everything, let y = x; with numbers would be painful. It is not. Types that live fully on the stack and are cheap to duplicate implement the Copy trait. Assigning them makes a real copy, and both variables stay usable.

Copied on assignment (Copy)Moved on assignment
All integers and floats: i32, u8, f64 ...String
bool and charVec<T>, HashMap, HashSet
Shared references &T, including &strBox<T> and other owning pointers
Tuples and arrays made only of Copy types, like (i32, bool) or [u8; 4]Your own structs and enums, unless you add #[derive(Clone, Copy)]

This lines up with JavaScript better than it looks. JS primitives (numbers, booleans) are copied. JS objects and arrays are shared by reference. In Rust the same "big" values are moved instead of shared.

clone: an explicit deep copy

When you really want two independent copies, ask for one with .clone(). It copies the heap data too, so it costs time and memory. That is why Rust makes you write it: a clone is always visible in the code.

Tip

As a beginner, cloning is fine. If the borrow checker blocks you and a .clone() makes the error go away, take it and keep going. Most programs are fast enough with a few extra clones. You can remove them later, once borrowing feels natural.

Passing values to functions moves them

Calling a function works like assignment. Passing a String into a function moves it into the parameter. When the function ends, the parameter goes out of scope and the text is freed. The caller cannot use it anymore.

A function can hand ownership back by returning the value. This works, but passing things in and out all the time gets clumsy fast.

The real fix for greet is to let the function look at the value without owning it. That is borrowing.

Borrowing with &

A reference lets code use a value without taking ownership. You make one with &. Rust calls this borrowing, because the value has to go back to its owner. When the borrow ends, nothing is freed. The owner still owns it.

The parameter type is &str, a borrowed piece of text. A &String turns into a &str for you, so greet(&name) works. Lesson 6 explains String and &str in detail.

Mental model

An owned value is a book you bought. A & reference is lending the book to a friend to read. They can read it, but they cannot write in it, give it away, or throw it out. And you must not burn the book while they are still reading.

Changing through a borrow with &mut

A plain & reference is read-only. To let a function change the value, pass a mutable reference with &mut. Both the variable and the reference need mut, so the change is visible at the call site.

With a mutable reference to a number, you write * to reach the value behind it. This is called dereferencing.

For method calls and field access you do not need the *. Rust adds it for you, which is why cart.push(...) works on a &mut Vec.

Many readers or one writer

This is the core rule of borrowing. At any moment, a value can have either:

  • any number of shared references (&T), or
  • exactly one mutable reference (&mut T).

Never both at once. A borrow lasts from where you create it to the last place you use it, not to the end of the block.

The bug this rule prevents

Changing a list while you loop over it is a real bug in JavaScript. It runs without an error and gives a wrong answer. In Rust the same code does not compile.

The loop holds a shared borrow of nums the whole time. remove needs a mutable borrow. The rule says you cannot have both, so the compiler stops you. Data races between threads are blocked by the same rule, which is why Rust can promise thread safety at compile time.

Drop, and why references never dangle

When an owner goes out of scope, Rust calls drop on its value, and the memory is freed right there. You can see the exact line where it happens: the closing brace.

Because Rust knows where every value dies, it can also check that no reference outlives the value it points to. A reference to freed memory is called a dangling reference. In C it is a common crash. In Rust it is a compile error.

JavaScript avoids this problem in a different way. The garbage collector keeps an object alive as long as anything points to it. Rust cannot do that without a collector, so it rejects the code instead.

Lifetimes, a first look

A lifetime is the stretch of code where a reference is valid. The compiler tracks lifetimes for every reference. Most of the time it works them out on its own and you never write them. You only write one when the compiler cannot tell how the references in a function relate.

The classic example is a function that returns one of two borrowed strings.

Read 'a as a name for "some stretch of code". The signature says: both inputs live at least for 'a, and the result is valid for 'a too. So the result can be used only while both inputs are still alive.

  • Lifetime names start with an apostrophe: 'a, 'b, 'de.
  • They go in angle brackets after the function name, like generics.
  • They never change how long anything lives. They only describe it so the compiler can check.
  • 'static means "valid for the whole program". String literals like "hi" have the type &'static str.

Tip

If you start adding lifetimes to structs to store references in them, stop and store owned values (String, Vec) instead. It is simpler, and it is what most real Rust code does.

Reading borrow checker errors

The borrow checker is the part of the compiler that checks these rules. You will meet the same handful of errors again and again. Here they are with the usual fix.

CodeMessageWhat happenedUsual fix
E0382borrow of moved value / use of moved valueYou used a variable after its value moved somewhere else.Pass &x instead of x, or call .clone() before the move.
E0499cannot borrow `x` as mutable more than once at a timeTwo &mut borrows overlap.Finish using the first one before making the second. Often a smaller block helps.
E0502cannot borrow `x` as mutable because it is also borrowed as immutableYou tried to change a value while someone is still reading it, like editing a Vec inside a loop over it.Collect what to change first, then change it. Or use a method like retain.
E0505cannot move out of `x` because it is borrowedYou moved a value while a reference to it is still in use.Use the reference before the move, or clone.
E0106missing lifetime specifierA function or struct returns or stores a reference, and the compiler cannot tell where it comes from.Return an owned value (String, Vec). If you really need the reference, add 'a.
E0597`x` does not live long enoughA reference outlives the value it points to.Move the value to an outer scope so it lives longer, or keep an owned copy.

Notice how the message tells the whole story: where the value was created, where it moved, and where you tried to use it after. The help line even offers a fix.

Rules of thumb for beginners

You do not need to master ownership before writing real code. These habits avoid most fights with the compiler.

SituationDo this
A function only reads textTake &str, not String or &String.
A function only reads a listTake &[T], not Vec<T> or &Vec<T>.
A function changes somethingTake &mut T.
A function creates something newReturn the owned value: String, Vec<T>, your struct.
A struct holds text or listsUse owned fields: String and Vec<T>, not references.
The borrow checker blocks you and you are stuckClone. Make it work first, make it fast later.
Several parts of the program really need to share one valueLook up Rc<T> (one thread) or Arc<T> (many threads). They count owners, a bit like a small garbage collector for one value.

Mental model

Before each function, ask one question: does it need to keep the value, change it, or just look at it? Keep means take it by value. Change means &mut. Look means &. That one question answers most ownership puzzles.

Check yourself

After let b = a; where a is a String, can you still use a?

No. The value moved to b, and using a gives error E0382. Use let b = a.clone(); if you need both.

Why is let y = x; fine when x is an i32?

i32 implements Copy. Assignment makes a cheap copy of the number, so both variables stay valid.

What type should a function take if it only prints a name?

&str. It only reads the text, so it borrows. The caller keeps ownership and can call it again.

Can you have a &v and a &mut v in use at the same time?

No. A value has many readers or one writer, never both. The compiler reports E0502.

When is the memory of a String freed?

At the closing brace of the scope where its owner lives. Rust calls drop there. No garbage collector is involved.

What does 'a in fn longest<'a>(...) do?

It names a lifetime, so the signature can say "the result lives as long as both inputs". It does not change how long anything lives. It only lets the compiler check the code.
