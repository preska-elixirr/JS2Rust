Async and fetching data

JavaScript gives you fetch and an event loop for free. Rust gives you the async and await syntax, and libraries do the rest. tokio runs async code, reqwest makes HTTP requests, and serde turns JSON into typed structs.

You will learn

  • Why Rust needs a runtime like tokio, and what #[tokio::main] does
  • How to GET and POST JSON with reqwest, and handle status codes and errors
  • Why serde protects you at runtime when TypeScript's as Post[] does not
  • Why Rust futures do nothing until you await them
  • The Rust versions of Promise.all, Promise.race, setTimeout and p-limit
  • How a small axum API compares to Express

Why Rust needs a runtime

Node and the browser always run an event loop. It waits for network replies and timers, then runs your callbacks. You never start it yourself. It is just there.

Rust ships the async and await keywords and the Future type, but no event loop. Rust keeps the core language small, so you choose the runtime as a library. Almost everyone picks tokio. It gives you the event loop, timers, network sockets, and a thread pool that runs tasks on all your CPU cores.

The features lists switch on optional parts of a crate. reqwest needs json for the .json() method. serde needs derive for #[derive(Deserialize)]. tokio's full turns on everything, which is fine while you learn.

What #[tokio::main] does

The program's main function cannot be async on its own, because nothing would run it. The #[tokio::main] attribute fixes that. It rewrites your code into a normal main that starts tokio and runs your async body inside it.

async and await syntax

The keywords mean the same thing as in JavaScript. Two details differ. .await goes after the value, like a field. And the return type of an async fn is the value it gives back, not a wrapper.

Postfix .await reads better in chains. In JavaScript you need extra parentheses to await in the middle of a chain. In Rust you just keep going left to right.

There is no .then() in everyday Rust. You use .await everywhere.

Tip

For a quick script where you do not want async at all, reqwest has a blocking client. Turn on the blocking feature and call reqwest::blocking::get(url)?.json()?. It is fine for small tools. Use the async client for servers and anything that makes many requests.

serde really checks the shape

This is one of the best reasons to like Rust for API work. In TypeScript, as Post[] is a promise you make to the compiler. Nobody checks it at runtime. The types are gone by then. If the API sends something else, your code carries on with bad data and crashes later, far away from the real cause.

serde checks every field while it parses. If the JSON does not match the struct, .json() returns an error right there, and it tells you what was wrong.

Mental model

A serde struct works like a zod schema and a TypeScript type in one. You write the shape once. You get the type for the compiler and a runtime check for free.

Shaping JSON fields

Real APIs are messy. Keys use camelCase, some fields are missing, some are null, some have odd names. serde attributes handle all of it.

AttributeWhat it does
#[serde(rename_all = "camelCase")]Maps every snake_case field to a camelCase key. Put it on the struct.
Option<T> fieldA missing key or null becomes None.
#[serde(default)]A missing key gets the type's default value: 0, "", empty Vec.
#[serde(rename = "e-mail")]Uses a different key for one field.
#[serde(skip_serializing_if = "Option::is_none")]Leaves the key out of the output JSON when the value is None.
#[serde(deny_unknown_fields)]Fails if the JSON has keys the struct does not list. By default serde ignores extra keys.

Tip

Only list the fields you need. If an API returns 40 fields and you use 3, your struct can have 3 fields. serde skips the rest.

Status codes and errors

Here is a surprise that is the same in both languages. A 404 or 500 response is not an error for fetch, and it is not an error for reqwest either. The request worked. The server just said no. You check the status yourself.

reqwest has a shortcut for this check. error_for_status() turns any 4xx or 5xx response into an Err, so a ? handles it.

Functions that fetch

The anyhow crate gives you one error type, anyhow::Error, that can hold any error. Return anyhow::Result<T> and every ? just works, whether the error came from reqwest, serde or your own code. It feels a lot like throwing in JavaScript, but the caller can see it in the type.

Add context to errors so the message says what you were doing. with_context wraps the original error with your own text.

Nothing goes over the network until .send(). Every method before it only builds up the request.

One client for the whole app

reqwest::get is handy for one request. For anything more, build one reqwest::Client and reuse it. The client keeps a pool of open connections, so later requests to the same server are faster. It is the same idea as an axios instance.

  • reqwest has no baseURL option. Keep the base in a constant and build URLs with format!.
  • The timeout covers the whole request. With plain fetch you would pass signal: AbortSignal.timeout(10_000).
  • client.clone() is cheap. All clones share the same connection pool. Clone it freely to pass it into functions and tasks.

Futures are lazy

This is the biggest difference from Promises, so read it twice. A JavaScript Promise starts working the moment you create it. A Rust future does nothing at all until you .await it or hand it to tokio::spawn.

A future is a recipe, not a running job. Calling load("a") only writes the recipe down. .await cooks it.

Trap

If you forget .await, the request never happens. In JavaScript a forgotten await still sends the request in the background. In Rust it silently sends nothing. The compiler warns you with "unused implementer of Future that must be used". Never ignore that warning.

Running things at the same time

Promise.all becomes join! and try_join!

tokio::join! runs several futures at once and waits for all of them. It gives you every result, like Promise.allSettled. tokio::try_join! stops at the first error, like Promise.all.

try_join! needs every future to have the same error type. With anyhow::Result everywhere, that is already true.

A list of futures

The macros take a fixed number of futures. For a list built at runtime, use join_all or try_join_all from the futures crate.

Promise.race becomes select!

tokio::select! waits for whichever future finishes first and runs that branch. A common use is a timeout.

One nice difference: the losing future gets dropped, which cancels it. In JavaScript the losing Promise keeps running in the background, and you just stop listening.

Trap

Do not use std::thread::sleep inside async code. It freezes the whole worker thread, and every other task on that thread stops with it. Always use tokio::time::sleep(...).await. The same goes for other blocking work like big file reads or heavy math. Move those into tokio::task::spawn_blocking.

tokio::spawn for background work

tokio::spawn starts a future right away as its own task, and it runs even if you never wait for it. That is the closest thing to calling an async function without await in JavaScript. It returns a handle you can await later to get the result.

A spawned task can outlive the function that started it, so it cannot borrow local variables. It must own everything it uses. That is why you write async move and clone what you need first.

Limiting how many run at once

Firing 1,000 requests at once can get you rate limited. In Node you might reach for p-limit. In Rust, turn the list into a stream and use buffer_unordered.

buffer_unordered gives results in the order they finish. Use buffered(5) if you need them in the original order.

Untyped JSON and JSON strings

Sometimes you do not want a struct. Maybe you only need one deep field, or the shape changes a lot. serde_json::Value holds any JSON, like any from res.json().

Indexing a Value with a key that does not exist gives Value::Null instead of crashing. So data["user"]["name"] works like data.user?.name. Then .as_str(), .as_i64() or .as_array() give you an Option with the real value. The json! macro lets you write JSON almost exactly like a JavaScript object.

JSON.stringify and JSON.parse

Both directions return a Result. Parsing can fail on bad input, and from_str checks the shape the same way .json() does.

Building an API: Express vs axum

You know how to write API routes in Express or Next.js. axum is the most popular Rust web framework, and it is built on tokio. Add axum = "0.8" to your dependencies next to tokio and serde.

  • A handler is a plain async fn. Its parameters say what it needs from the request. Path<u32> reads the {id} part of the URL. Json<NewUser> reads and checks the body.
  • If the id is not a number or the body has the wrong shape, axum answers with a 400 or 422 error before your handler runs. You do not write that check.
  • Whatever the handler returns becomes the response. A &str becomes text, Json(x) becomes JSON, and a tuple with a StatusCode sets the status.
  • A Next.js file at app/api/users/[id]/route.ts with a GET export maps to .route("/users/{id}", get(get_user)). axum 0.8 writes path parameters as {id}. Older tutorials use :id, which no longer works.

Check yourself

What happens when you write let f = get_post(1); and never use f?

Nothing. A Rust future is lazy, so no request is sent. The compiler warns that the future is unused. Add .await, or pass it to tokio::spawn to run it in the background.

Does reqwest return an Err when the server answers 404?

No. Like fetch, it treats any answer as a success. Call .error_for_status()? or check res.status().is_success().

What is the Rust version of await Promise.all([a(), b()])?

tokio::try_join!(a(), b())?. For a list built at runtime, use futures::future::try_join_all.

Why does res.json() as Post[] not protect you, while serde does?

TypeScript removes types before the code runs, so as checks nothing at runtime. serde checks every field while it parses and returns an error when the JSON does not match the struct.

Which attribute maps the JSON key userId to the field user_id?

#[serde(rename_all = "camelCase")] on the struct. For a single odd key, use #[serde(rename = "...")] on the field.

Why is std::thread::sleep a bad idea inside an async function?

It blocks the worker thread, so every other task on that thread stops too. Use tokio::time::sleep(duration).await, which lets other tasks run while you wait.
